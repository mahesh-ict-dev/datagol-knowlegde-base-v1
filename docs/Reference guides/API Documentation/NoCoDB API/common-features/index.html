Common Features

This section describes common features and patterns used across all NoCoDB API versions.

Authentication​

All NoCoDB APIs require JWT authentication with the s_jwt security requirement.

Authentication Header​

Authorization: Bearer YOUR_JWT_TOKEN

Example Request​

curl -X GET "noCo/api/v2/workspaces" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

Error Handling​

Standard HTTP Status Codes​

  • 200 OK - Request successful
  • 201 Created - Resource created successfully
  • 400 Bad Request - Invalid request parameters
  • 401 Unauthorized - Authentication required
  • 403 Forbidden - Insufficient permissions
  • 404 Not Found - Resource not found
  • 409 Conflict - Resource conflict
  • 422 Unprocessable Entity - Validation errors
  • 500 Internal Server Error - Server error

Error Response Format​

{
  "error": "string",
  "message": "string",
  "timestamp": "date",
  "path": "string",
  "details": {
    "field": "string",
    "value": "string",
    "constraint": "string"
  }
}

Example Error Response​

{
  "error": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "timestamp": "2024-01-15T10:30:00.000Z",
  "path": "/noCo/api/v2/workspaces",
  "details": {
    "field": "name",
    "value": "",
    "constraint": "must not be empty"
  }
}

Request/Response Format​

JSON Request/Response Bodies​

All APIs use JSON for request and response bodies.

Content-Type Header​

Content-Type: application/json

Consistent DTO Structures​

All APIs follow consistent data transfer object (DTO) patterns:

{
  "id": "string",
  "name": "string",
  "description": "string",
  "createdAt": "date",
  "updatedAt": "date",
  "createdBy": "string",
  "updatedBy": "string"
}

Validation Annotations​

APIs use standard validation annotations:

  • @NotNull - Required fields
  • @Size(min, max) - String length constraints
  • @Min, @Max - Numeric constraints
  • @Email - Email format validation
  • @Pattern - Regex pattern validation

Pagination​

Pagination Parameters​

  • page - Page number (0-based, default: 0)
  • size - Page size (default: 20, max: 100)
  • sort - Sort field and direction (e.g., "createdAt,desc")

Paginated Response Format​

{
  "content": [
    {
      "id": "string",
      "name": "string"
    }
  ],
  "pageable": {
    "pageNumber": 0,
    "pageSize": 20,
    "sort": {
      "sorted": true,
      "unsorted": false
    }
  },
  "totalElements": 100,
  "totalPages": 5,
  "last": false,
  "first": true,
  "numberOfElements": 20,
  "size": 20,
  "number": 0,
  "sort": {
    "sorted": true,
    "unsorted": false
  }
}

Example Paginated Request​

curl -X GET "noCo/api/v2/workspaces?page=0&size=10&sort=createdAt,desc" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN"

File Upload​

Multipart File Upload Support​

APIs support multipart file uploads for various file types.

Supported File Formats​

  • CSV files
  • Excel files (.xlsx, .xls)
  • JSON files
  • Text files
  • Image files

File Upload Example​

curl -X POST "noCo/api/v2/workspaces/{workspaceId}/tables/csvUpload" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -F "file=@data.csv" \
  -F "tableName=my_table" \
  -F "description=Uploaded data"

File Validation​

  • File size limits
  • File type validation
  • Content validation
  • Virus scanning (where applicable)

Permissions​

Role-Based Access Control (RBAC)​

NoCoDB implements a comprehensive RBAC system:

User Roles​

  • Owner - Full access to workspace and all resources
  • Admin - Administrative access to workspace
  • Editor - Can edit and manage resources
  • Viewer - Read-only access to resources
  • Guest - Limited access to shared resources

Permission Levels​

  • Workspace Level - Permissions scoped to entire workspace
  • Element Level - Permissions for specific tables, pages, widgets
  • Row Level - Permissions for specific data rows
  • Column Level - Permissions for specific columns

Permission Inheritance​

Workspace Permissions
├── Table Permissions
│   ├── Row Permissions
│   └── Column Permissions
├── Page Permissions
│   └── Widget Permissions
└── Folder Permissions
    └── Element Permissions

Permission Checking​

{
  "userId": "string",
  "elementType": "TABLE",
  "elementId": "string",
  "permissions": ["READ", "WRITE", "DELETE"],
  "granted": true
}

Rate Limiting​

Rate Limit Headers​

  • X-RateLimit-Limit - Maximum requests per time window
  • X-RateLimit-Remaining - Remaining requests in current window
  • X-RateLimit-Reset - Time when the rate limit resets

Rate Limit Response​

{
  "error": "RATE_LIMIT_EXCEEDED",
  "message": "Rate limit exceeded. Please try again later.",
  "retryAfter": 60
}

Caching​

Cache Headers​

  • ETag - Entity tag for cache validation
  • Last-Modified - Last modification time
  • Cache-Control - Cache control directives

Conditional Requests​

# Check if resource has changed
curl -X GET "noCo/api/v2/workspaces/{workspaceId}" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -H "If-None-Match: \"abc123\""

Webhooks​

Webhook Configuration​

{
  "id": "string",
  "name": "string",
  "url": "string",
  "events": ["CREATE", "UPDATE", "DELETE"],
  "headers": {
    "Authorization": "Bearer webhook_token"
  },
  "active": true
}

Webhook Payload​

{
  "event": "CREATE",
  "timestamp": "2024-01-15T10:30:00.000Z",
  "data": {
    "id": "string",
    "name": "string",
    "type": "TABLE"
  },
  "workspaceId": "string"
}

Search and Filtering​

Search Parameters​

  • q - Search query
  • type - Resource type filter
  • status - Status filter
  • createdBy - Creator filter
  • dateRange - Date range filter

Search Example​

curl -X GET "noCo/api/v2/workspaces/search?q=sales&type=TABLE" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN"

Advanced Filtering​

{
  "filters": [
    {
      "field": "name",
      "operator": "CONTAINS",
      "value": "sales"
    },
    {
      "field": "createdAt",
      "operator": "GREATER_THAN",
      "value": "2024-01-01T00:00:00.000Z"
    }
  ],
  "sort": {
    "field": "createdAt",
    "direction": "DESC"
  }
}

Bulk Operations​

Bulk Create​

{
  "items": [
    {
      "name": "Item 1",
      "description": "Description 1"
    },
    {
      "name": "Item 2", 
      "description": "Description 2"
    }
  ]

Bulk Update​

{
  "updates": [
    {
      "id": "item1",
      "name": "Updated Item 1"
    },
    {
      "id": "item2",
      "description": "Updated Description 2"
    }
  ]

Bulk Delete​

{
  "ids": ["item1", "item2", "item3"]
}

Best Practices​

Request Optimization​

  1. Use Pagination - Always paginate large result sets
  2. Selective Fields - Request only needed fields
  3. Batch Operations - Use bulk APIs for multiple operations
  4. Conditional Requests - Use ETags for cache optimization

Error Handling​

  1. Check Status Codes - Always verify HTTP status codes
  2. Handle Rate Limits - Implement exponential backoff
  3. Validate Responses - Validate response data structure
  4. Log Errors - Log error details for debugging

Security​

  1. Secure Token Storage - Store JWT tokens securely
  2. Token Refresh - Implement token refresh logic
  3. Input Validation - Validate all input data
  4. HTTPS Only - Always use HTTPS in production

Performance​

  1. Connection Pooling - Reuse HTTP connections
  2. Request Batching - Batch related requests
  3. Caching - Cache frequently accessed data
  4. Async Operations - Use async/await for better performance
